## Implications for the rebuild

- Represent lessons as a typed, declarative document format (Camperdown-like: strict markup, command blocks, embedded widget references) that compiles or interprets into an interactive runtime. Never store lessons as free-form HTML. This keeps content diffable, LLM-generatable and validatable.
- Model every interactive as a parametric generator with a declared input list (sliders, draggable points, time) and a pure state-to-view function, following the Diagrammar pattern. Allow widgets to subscribe to each other's state so one lesson page can wire several manipulatives together.
- Build answer checking as a composable validator ('expectations') library over a symbolic math representation (MathJSON-style), with field-level feedback messages. The MIT-licensed cortex-js compute-engine and MathLive are candidate local dependencies; flag them for user approval per the G3 rule before adopting.
- Keep the LLM's role narrow. The deterministic engine owns math correctness and solvability. The LLM emits configs in an LLM-friendly representation, and solvers or eval checks gate every item before the user sees it. Invest in representation design before model choice, since Brilliant got 0% to 93% success from representation changes alone.
- Implement the tutor as a tool-calling agent over live lesson state (current widget state, attempt history, pause time). Tools: highlight, annotate, add point, pose an intermediate question, swap to a simpler variant. Each concept carries authored 'tutor notes' listing common misconceptions, allowed tools and help strategies. Policy: speak first on each page about what changed, keep replies short, never give the answer, withdraw entirely on test or mastery items.
- Generate speech text and audio separately, and verify spoken numerals and expressions against the script, because a wrong spoken number is catastrophic. Drive the tutor character from a small state machine (idle, wave, nod, react-easy, react-struggle, celebrate) with an audio-amplitude parameter for 'talking'. Lottie or Rive can be local options.
- Use a coded skill graph (Big Idea → learning objective → skill, with stable IDs like PSV-1 and worked examples) as the backbone for every STEM domain. Map lessons and problems to skills many-to-many.
- Ship a coverage audit view (Covered/Partial/Gap; coverage = (C + 0.5P)/Total) per domain. It shows where breadth is missing (physics, chemistry, biology, electronics) and drives targeted generation of missing lessons, directly addressing Brilliant's narrowed catalog.
- Log every answer choice, hint request, pause and session event locally (e.g., SQLite) from day one. Start with a simple per-skill mastery model (Elo/BKT-style) plus a next-problem selector that targets readiness for a future item Y, with spacing, interleaving and automaticity (speed plus accuracy) tracking. Deep recommenders are unnecessary for a single user.
- Support 'ask the tutor to find a lesson': free-text intent is mapped onto skill-graph nodes, then a custom learning path is assembled from prerequisites. This becomes the mechanism for user-requested custom paths.
- Prioritize adaptive difficulty and content quality over Skinner-box gamification. Brilliant's own data says mechanics barely moved engagement and difficulty matching did. Streaks and XP are cheap secondary features; leagues make little sense single-user.
- Run content production as a pipeline: golden hand-made examples → LLM generation → automated evals (correctness, unique solvability, visual clarity, impossible states) → user/curator review → a variation tool for practice sets. Track drift and regressions across generator versions.
- Version courses and keep retired content in an archive instead of deleting it, with progress migration across course revisions. This avoids the user-trust problem Brilliant created by silently removing courses.
